The brief

What you know going in

The profile feature throws errors in bursts and then goes quiet, over and over. The host is healthy and no dependency is failing. Deployments are being recorded in New Relic as change-tracking markers. Use them to answer the only question that matters here: did a change cause this?

Correlation method
  • Localize an error spike to one transaction in APM.
  • Overlay deployment markers on your charts with change tracking.
  • Correlate each error burst with the deploy that preceded it.
  • Confirm the specific new error in Errors Inbox and pin it to a release.
Before you start
  • New RelicAccess to the account the site reports to (the one in nr-config.js).
  • Error windowThe errors run for the second quarter of each hour (about :30–:44 UTC), with a deploy marker at the start. If it's quiet, widen each query's SINCE to find the last burst.

Step 1 of 6

Step 1 · Confirm and localize

Users report errors on their profile. What confirms it and shows which part of the app?

An error problem is an error-rate question. APM (and Errors Inbox) show the rate over time and which transaction is throwing: here it's /api/profile, erroring in bursts.

See it in New Relic

Find the error spike and its transaction

In APM & services → the demo service, look at the error rate, or open Errors Inbox. /api/profile throws in sharp bursts with clean gaps between, which already hints at something switching on and off, like a release.


            

          

        


        
        

          

            
Step 2 · Ask the right question

            
The errors come in abrupt bursts, then stop. For errors that appear and vanish like that, what's the first thing to check?

            

              
              
              
            

            
Errors that start abruptly and come and go usually follow a change. Before chasing infrastructure, check whether a deploy coincides. New Relic's change tracking puts deployment markers right on your charts for exactly this.

          

          

            See it in New Relic
            
Put deployments on the chart

            
On the service, open Deployments / Change tracking, or turn on the deployment markers on the error chart. Each marker is a recorded release. Now line them up against the error bursts.

          

        


        
        

          

            
Step 3 · Read the correlation

            
With deployment markers on the error chart, what do you see?

            

              
              
              
            

            
Every spike starts just after a marker. That timing is a strong signal: the change shipped, then the errors began. It doesn't prove cause on its own, but it tells you exactly which release to look at.

          

          

            See it in New Relic
            
The markers precede the spikes

            
List the deployment markers and compare their times to the error bursts from step 1. Each burst follows a marker. The markers carry a version, so you know which release to suspect.

            

            

          

        


        
        

          

            
Step 4 · Identify the error

            
A deploy lines up with the spike. What does Errors Inbox tell you about the error itself?

            

              
              
              
            

            
Errors Inbox shows a TypeError: Cannot read properties of undefined (reading 'tier'), a null reference, appearing in the same windows. That's the kind of bug a code change introduces: the new version reads a field off something that isn't always there.

Step 5 · Name the root cause

            
Infra is healthy, no dependency is failing, and a null-reference error appears only after a deploy. What's the root cause?

            

              
              
              
            

            
The new version has a bug: it reads a field off an object that's sometimes undefined. It's a code regression, and change tracking pinned it to a specific release. "Fix the infrastructure" would have gone nowhere.

          

          

            The reasoning
            
A regression, tied to a release

            
Healthy host, healthy dependencies, a brand-new null-reference error that starts at a deploy: that's a code regression. The marker tells you which deploy introduced it, so you're not guessing which change to revert.

          

        


        
        

          

            
Step 6 · What next

            
You've tied the errors to a deploy and identified the bug. What's the move?

            

              
              
              
            

            
Roll back the bad version, or ship a fix, using the marker to know exactly which release. Then alert on the new error group and add a guard for the missing field, so the next regression is caught in minutes, not by users.

          

          

            The takeaway
            
"What changed?" should have an answer

            
Recording deployments is what turns "errors are up, no idea why" into "this release, at this time, introduced this error." That's the whole point of change tracking.
