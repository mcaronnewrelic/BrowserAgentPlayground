Handle methods vs. top-level calls

Two different APIs telling one story

newrelic.interaction([options]) (Pro+SPA v963+) returns a handle bound to whatever interaction is currently in progress, or a new API-driven one if nothing is. The agent prioritizes real clicks: if one is already running, you get a handle to that, not a new one. An API-created interaction with no waitForEnd has no 30-second timeout the way a click does; it just sits open until something else displaces it, which is why the demos below always pair .save() or .ignore() with .end().

Chained off that handle: .setName(name, trigger), .actionText(text), .setAttribute(key, value), .save() (forces the interaction to be reported even if the route+DOM heuristic was never met), .ignore() (forces it to never be reported, even if the heuristic would have passed), and .end().

setCurrentRouteName(name) (v998+) and setPageViewName(name, host) (v593+) and finished(time) (v593+) are not handle methods. They're separate top-level newrelic.X() calls that happen to be part of the same "control it yourself" story. setCurrentRouteName() labels the SPA interaction's route; setPageViewName() renames the initial PageView, a different event entirely; finished() is a timing marker, unrelated to either.

1 · Force a save

interaction().save().end()

Opening a settings panel is purely client-side: no route change, no AJAX. On events.html, that kind of click could never become its own BrowserInteraction. .save() forces it anyway.

2 · Suppress on purpose

interaction().ignore()

Changes the URL, then updates this card: the exact recipe that normally qualifies as a BrowserInteraction. .ignore() kills it anyway. It will not show up in the queries below.

3 · Name the route yourself

setCurrentRouteName()

Names the route as a pattern, alternating between /spa-demo/:code and /spa-demo/:code/detail on each click, not literal URLs, then changes it. Real SPA routers call this every time a route changes; a static site has to fake the "every time" part by hand. The alternation is what makes previousRouteName and targetRouteName actually differ, instead of landing on the same string every time.

4 · Mark it finished

finished()

A timing marker for "the page is done, by my own definition," not the browser's load event. Useful for pages that keep loading content asynchronously after the page technically finishes loading.

5 · Already ran, no button

setPageViewName()

The docs are explicit: this one only works if it's called before the window load event fires. By the time you could click a button, that's already happened. So this page called it automatically, the moment it loaded.
