The brief

What you know going in

The site runs on one small host: the demo app in a container, next to the New Relic infrastructure agent that reports the host and everything on it. Something else on that host misbehaves on a schedule. Work the chain and the data will tell you what.

You'll learn to
Diagnosis method
  • Localize a slowdown to one service and one transaction in APM.
  • Tell a resource problem apart from a code problem.
  • Follow an entity's relationships down to the container and host it runs on.
  • Read host CPU and load, and find the process to blame in ProcessSample.
Before you start
  • New RelicAccess to the account the site reports to (the one in nr-config.js).
  • Host loadThe host needs to be under the daily "noisy neighbor" load (or ask your instructor to run it). If it's quiet, widen each query's SINCE to find the last burst.
  • Process metricsThe infrastructure agent must report ProcessSample for the final step. It does on this host.
Work the chain / Checkpoints

Step 1 of 6

Step 1 · Confirm and localize

Support says "the site is slow." Where do you look first to confirm it and narrow it down?

"Slow" is a response-time question. The APM service shows its response time over time, so you can confirm the slowdown is real and see exactly when it happens before chasing anything else.

See it in New Relic

Open the APM service and watch response time

Open APM & services → the demo service and look at the response-time chart. You'll see flat, fast baseline with sharp spikes that come and go. Note when a spike happens; you'll line the other tiers up against it.

Step 2 · Find the transaction

            
The service's response time spikes on and off. How do you find which endpoint is behind the spikes?

            

              
              
              
            

            
Faceting response time by transaction name points straight at the offender. Here it's /api/recommendations: it jumps from about 160 ms to well over half a second during the spikes, while the other endpoints stay flat.

          

          

            See it in New Relic
            
Response time by transaction

            
In the service, open Transactions, or run the query below. One transaction, /api/recommendations, accounts for the spikes. That's a clue in itself: it's the endpoint that does real computation, so it's the one that suffers when CPU is scarce.

            

            

          

        


        
        

          

            
Step 3 · Code or resource?

            
The slow endpoint comes and goes, in bursts, with no deploy between fast and slow. What does that pattern point to?

            

              
              
              
            

            
Code that didn't change doesn't get intermittently slower on its own. Latency that comes and goes in bursts, with the same code, almost always means a shared resource (CPU, memory, I/O) is being contended. So the next move is down a tier, to where the service actually runs.

          

          

            The reasoning
            
Rule out the code, look at the infrastructure

            
No deploy, intermittent, bursty: that's the signature of resource contention, not a logic bug. The recommendations endpoint is CPU-bound, so when something steals CPU, it's the first to feel it. Follow the service down to the machine it shares.

          

        


        
        

          

            
Step 4 · Follow the entities

            
You want to get from the slow service to the infrastructure it depends on. What's the fastest honest way there in New Relic?

            

              
              
              
            

            
New Relic links entities that depend on each other. From the service, Related entities (and the service map) takes you straight to the container it runs in and the host underneath, with no guessing which machine.

          

          

            See it in New Relic
            
Service → container → host

            
On the service, open Related entities or the service map and follow the links down: the service runs in a container, and the container runs on a host. Open that host entity. Everything from here on is about the host, which is shared by whatever else happens to run on it.

          

        


        
        

          

            
Step 5 · Read the host

            
On the host, which reading best confirms CPU contention lined up with the slow periods?

            

              
              
              
            

            
CPU pinned near 100% with a load average well above the core count means processes are queued waiting for CPU. When those windows line up with the recommendations spikes, you've connected the app symptom to the host.

          

          

            See it in New Relic
            
Host CPU and load average

            
On the host, the CPU chart sits near 100% during the spikes and the load average climbs well past the number of cores. Same windows as the recommendations slowdown. The host is starved; now find what's eating it.

            

            

          

        


        
        

          

            
Step 6 · Name the culprit

            
The host CPU is pegged. How do you find the process responsible, and what do you expect to see?

            

              
              
              
            

            
Faceting ProcessSample by process shows the truth: a single process named noisy-neighbor sits at the top of CPU during every burst, and it isn't part of the app at all. The recommendations endpoint was never broken; a neighbor on the shared host was taking its CPU.

          

          

            See it in New Relic
            
CPU by process on the host

            
Open Processes on the host, or run the query below. During the bursts, a process called noisy-neighbor dominates CPU, far above the app's own container processes. That's your culprit, found by following the chain, not by guessing.

Case closed

        
The app was innocent. A noisy neighbor took its CPU.

        
The recommendations endpoint slowed down because a process named noisy-neighbor on the same host spiked CPU to 100% on a schedule, starving the app's container. Nothing in the app changed. You proved it by following one chain: slow request → APM service → its transaction → container → host → the process on top.

        
What you'd do next in the real world:

        
    
          
  • Identify and stop the rogue process, and find out who or what started it.
    • 
          
  • Stop it recurring with resource isolation: CPU limits on containers, requests and limits in Kubernetes, or moving a hungry workload to its own host.
    • 
          
  • Add an alert on host CPU or load so the next noisy neighbor pages someone before customers feel it.
    • 
        

        
Why it worked: entity relationships let you follow real dependencies across tiers, so a browser-side symptom leads all the way to a process on a host, without guessing.
